## 起点

昨天我的博客还是一个普通的 Astro 模板——标准的大图 + 标题布局，与"个人作品集"的定位格格不入。昨晚我决定动一次大手术，把整个站点改成 Matrix 终端风格，并加入一些有趣的功能。

这便是那场折腾的全记录。

## 第一幕：终端美学的全面改造

### 设计语言

整个站点被重新定义为绿色终端美学：

- **背景**：纯黑 `#000000`
- **字体**：等宽字体（Courier New）+ 磷光绿 `#00ff41`
- **特效**：glow 阴影、CRT 扫描线叠加、Matrix 数字雨动画
- **图片**：全部移除，替换为 ASCII 艺术字

主页从"居中终端窗口"变成了完整的作品集布局：导航栏 → Hero 区域 → 专业领域 → 探索思考 → 最新动态 → 页脚。 bilingual 内容（中英双语）贯穿始终。

### 全站统一

不只是主页。博客列表页变成了 `ls -la` 风格的文件列表，文章页用 ASCII art 边框装饰，关于页用终端命令展示个人信息（`> whoami`、`> cat ~/.stack`）。所有页面共享同一套设计语言。

## 第二幕：base 路径的坑

Astro 配置中 `base: '/my-blog'` 导致资源路径全部错位。原因很简单：使用自定义域名时，GitHub Pages 从域名根目录 `/` 提供服务，而不是 `/my-blog`。改成 `base: '/'` 后一切正常。

教训：**base 路径取决于你的部署方式**，不是所有场景都适用默认值。

## 第三幕：gh-pages 的噩梦与救赎

### 问题

使用 `gh-pages` npm 包部署时，构建反复失败——持续时间 0ms，说明是验证错误而非内容错误。

### 根因

`gh-pages` 分支上积累了不属于 `dist/` 的多余文件：`.vscode`、`.wrangler`、`.gitignore`。这些是之前部署的残留，GitHub Pages 构建时处理这些文件失败。

### 解决

删除并重建 `gh-pages` 分支，只保留 `dist/` 内容。构建时间从"永远卡死"变成了 8 秒。

### 升级：切换到 GitHub Actions

既然要重建分支，不如彻底升级部署流程。创建 `.github/workflows/deploy.yml`：

- **build** 任务：checkout → 安装 Node 22 → `npm ci` → `npm run build` → 上传 artifact
- **deploy** 任务：`actions/deploy-pages@v4` 自动部署

通过 API 将 GitHub Pages 源从 branch 切换为 workflow。以后只需 `git push origin main`，几秒钟完成部署。

## 第五幕：ASCII 艺术字的血泪史

这是今天最曲折的部分。

### 第一次尝试

用户提供了一段 ASCII 艺术字，我直接用它替换了导航栏文字。结果：
1. 位置错了——应该替换 Hero 区域的大标题，而不是导航栏
2. 字形不对——那段 ASCII 并不能清晰辨认出 "NORTHERNHIWISEN"

### 第二次尝试

使用 figlet "ANSI Shadow" 字体重新生成。这次字形正确了，但放在了导航栏（错误位置）。

### 第三次尝试

修正位置：导航栏保持文字 "Northernhiwisen"，Hero 区域放 ASCII 艺术字。

### 第四次修正

用户指出艺术字不清晰。最终用 figlet 生成了正确的 "ANSI Shadow" 字体版本，并居中显示。

## 经验总结

1. **部署方式决定一切**：GitHub Actions 远比 `gh-pages` 包可靠，日志透明，部署快速
2. **CDN 缓存是隐形的敌人**：Fastly 缓存 404 响应，导致修复后仍显示旧错误
3. **分支管理要干净**：`gh-pages` 分支只应包含构建产物，多余文件会导致构建失败
4. **密码策略要实用**：我们讨论了多种方案，最终选择了最实用的一种
5. **ASCII 艺术字要验证**：不要假设提供的艺术字是正确的，用 figlet 生成标准字体更可靠
6. **AI 协作的效率**：今天完成了过去可能需要数天的工作——从设计到部署到各种功能

折腾本身，就是乐趣的一部分。
